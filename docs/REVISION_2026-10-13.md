## Finding d2d6b0db (medium, reproduced, fixed): stage 1 accepted services stage 2 refuses

**Report.** On chain 11155111 `deployCompanions` and `configureAndActivate` require the factory, pool manager,
fees and registry code hashes to equal the `SepoliaRelease` pins, but `beforeInitialize` checked only the sender
and the key shape. A launch through unpinned services therefore succeeded at stage 1, locked the 87% seed in a
position that can never shrink, and could never activate. The reviewer's proof
(`Proof_d2d6b0dbd9b5.t.sol`) failed on the starting tree with `next call did not revert as expected`.

**Reproduction.** Confirmed: the proof fails on the starting tree exactly as reported.

**Fix** (`src/UnlkHook.sol`).

* `beforeInitialize` now calls `_verifyServices()` after the key-shape checks, so on Sepolia the launch transaction
  itself reverts with `InvalidConfig` when the factory, manager, fees or registry is not the pinned code.
  On any other chain id the pins are not consulted, as before.
* `_verifyServices` is the single place for the four Sepolia service pins. It now includes the registry
  (`factory.registry().codehash == SepoliaRelease.REGISTRY`), which `_verifyLaunchRecord` previously checked
  separately with `InvalidEvidence`; that duplicate was removed. `_verifyLaunch` still runs `_verifyServices`
  first, so stage 2 checks the same four pins it did before, now reporting a registry mismatch as
  `InvalidConfig` from the earlier check.
* The factory's code hash is compared first, so `fees()` and `registry()` are only read from the pinned factory
  code. The real `LaunchFactory` exposes both as view getters; the fork rehearsal below exercises them inside the
  real factory's `launch` transaction.

**Evidence.**

* The reviewer's proof passes on the revised tree.
* `test/SepoliaPins.t.sol` (8 tests): local services on chain 11155111 are refused with the exact error and the
  hook stays unbound; each single unpinned or lookalike service (manager, factory, fees, registry) is refused;
  the pinned code accepts. The accepting path etches the recorded runtime bytes of the four Sepolia services
  (`test/fixtures/SepoliaRuntime.sol`, copied from `docs/network/*.runtime.hex`, each asserted to hash to its
  pin) at their public addresses and initializes through the real `PoolManager` code with the real factory
  address as sender. On the default local chain id the same unpinned fixtures initialize as before.
* Recorded-block fork, both stages, through the real Sepolia factory (`delivery/checks/revision-fork.txt`):
  block **11906030**, hash `0x6f28f1fbf63d2f156df99f6aa68b5cda5b4af8bec7d5a488b6057dddf7b98a40`, public endpoint
  `https://ethereum-sepolia-rpc.publicnode.com`, harness `delivery/rehearsal/RecordedSepolia.t.sol` with only
  the recorded block number substituted. Impersonated signer, synthetic launch number and one-leaf tree, as
  documented for that harness; the logged addresses are fork-only.

## Finding 9224491b (low, advisory, judged real, fixed): a reserve-draining sell walked the price to tick 887271

**Report.** The official pool's only liquidity is the factory's token-only seed. An exact-input sell larger than
the pool's ETH reserve consumed the in-range ETH, then v4 stepped the price through the empty region to the
caller's limit (clients pass `MAX_SQRT_PRICE - 1`). The checkpoint recorded `liquid = false`, `twapTick` reverted
for a full two-hour window after the price recovered, and a confirmation run in progress restarted, although the
pool's economic state equalled the launch state, which is classed liquid.

**Reproduction.** Confirmed on the starting tree with the reviewer's steps (alice buys 0.05 ETH, `syncPayer`, the
payer sells its whole quota exact-input at the open limit): `slot0.tick == 887271`, the last observation
illiquid, `fdvUsd` reverting two hours later.

**Judgement.** Real. Draining the reserve and buying back a block later costs only two LP fees on the reserve and
blocks tier confirmation for two hours, far cheaper than the disclosed sustained-price manipulation. On Sepolia
the seed range is provably the only liquidity: the verified `LaunchFactory` ABI reaches the manager's callback
only from `launch` and `claimFees`, and the hook admits no other liquidity provider.

**Fix** (`src/UnlkSwapRouter.sol`, `src/interfaces/IIntegration.sol`). The router bounds every swap's price limit
to the seed range it reads from the hook (`seedTickLower()` / `seedTickUpper()`, public getters that already
existed; the hook's ABI is unchanged). A sell stops exactly at the seed's upper boundary, the launch state, and a
buy at its lower boundary. Partial fills, quota accounting, settlement and the operation hash are unchanged; a
tighter caller limit still applies. The TWAP, feed, depth and sequential-confirmation rules were not touched.

**Evidence.** `test/SeedBoundary.t.sol` (4 tests): the reviewer's drain stops at the boundary with the
observation liquid and the FDV readable after a window; a sell into an empty reserve reverts without state; a
caller limit inside the range is honoured; a buy at the open limit is unaffected. Two accepted tests in
`test/CreditsAndFees.t.sol` sold from the launch state into the fixture's local-only ETH depth placed above the
seed boundary (`_localQuoteDepth`, documented as impossible on a real chain); they now make the fixture's
non-actor warm-up buy first so the sale has a real reserve, and assert the same credit behaviour.
